## 1. 시스템 이해 요약

### 1.1 시스템 이름 및 목적

**SQA P1 Workflow** (`package.json`의 `sqa-p1-workflow`).

약 10명 규모 파트(파트장 1명 + 파트원 다수)에서 발생하는 다음 업무 문제를 해결하기 위한 내부용 웹 시스템이다.

1. 파트원별 담당제품·담당업무(정기 업무)가 어디에도 정리되어 있지 않아 파트장이 배정 현황을 한눈에 볼 수 없음
2. 파트원 → 파트장 검토요청이 메신저·메일에 흩어져 상태(대기중/완료/반려)와 기한 관리가 안 됨
3. 프로젝트성(논루틴) 업무의 배정과 마감이 개인 기억에 의존함

### 1.2 주요 사용자

| 역할 | 권한 요약 |
|---|---|
| 파트장 (`leader`) | 전체 조회, 마스터 데이터(제품/업무/초대) 관리, 배정, 검토 피드백·상태 변경, 프로젝트 생성·수정 |
| 파트원 (`member`) | 본인 담당·배정·검토요청만 조회, 검토요청 생성 |

권한은 프론트엔드 분기(`src/domain/permissions.ts`)와 Supabase RLS(`supabase/migrations/202607020001_initial_schema.sql`, `202607040002_harden_role_invariants.sql`) 양쪽에서 강제된다.

### 1.3 핵심 업무 흐름

1. **온보딩**: 파트장이 `allowed_users`에 이메일 등록 → 해당 이메일로 가입/로그인 시 DB 트리거(`handle_new_user`, `handle_allowed_user_saved`)가 `profiles` 자동 생성 → `must_change_password` 플래그로 첫 로그인 시 비밀번호 변경 강제(`PasswordChangePanel` + `mark_password_changed` RPC)
2. **검토요청**: 파트원이 제목/설명/첨부링크/기한으로 요청 생성(`pending`) → 파트장 우선처리 큐에 노출 → 파트장이 `pending` 상태에서 피드백 작성(상태 유지) → `approved`/`rejected`로 종결 → 파트원이 결과 확인
3. **프로젝트 배정**: 파트장이 프로젝트 생성 시 파트원 동시 배정(워크로드 미리보기 제공) → 파트원 화면에 본인 배정만 노출 → 마감 14일 전부터 리마인더 큐에 표시
4. **기초데이터 관리**: 파트장이 제품/업무 카테고리 등록 → 파트원에게 배정 → 미배정 제품/배정 공백 파트원이 대시보드에 경고로 노출

### 1.5 현재 구조의 장점

1. **DB 단 권한 강제가 탄탄함**: RLS + `security definer` 함수 + 역할 불변식 트리거(`202607040002`)로, 프론트엔드가 뚫려도 데이터 접근이 차단되는 구조. `docs/TEST_PLAN.md`에 RLS 수동 검증 시나리오도 문서화되어 있음.
2. **데모 모드**: 환경변수 없이 `createPreviewData()`로 전체 UI를 역할 전환까지 체험 가능 — 개발·시연·회귀 확인에 유리.
3. **작지만 정확한 테스트**: `formatDate`의 날짜-경계 버그 방지 테스트, RLS 정책 텍스트 회귀 테스트(`migrations.test.ts`), 권한 유틸 테스트가 존재.
4. **보안 기본기**: CSV 수식 인젝션 방지, 첨부 URL http/https 검증(`normalizeHttpUrl`), service role key 미사용 원칙 문서화.
5. **업무 관점의 UI 발상**: 우선처리 큐(기한+대기일 점수), 배정 시 워크로드 미리보기, 미배정 경고 등 "파트장이 아침에 무엇부터 볼지"를 설계에 반영.

### 1.6 현재 구조의 한계

1. **`src/App.tsx` 단일 파일 4,336줄**: 화면 10여 개, 데이터 로딩, 뮤테이션, 데모 분기가 전부 한 파일. 여기에 **렌더링되지 않는 데드코드**가 대량 포함됨 — `AdminPanel`(3665~4220행, 약 555줄), `OperationsGuide`(4222~4243행), `Dashboard`의 leader 분기(1312~1562행), `Shell`의 구 `tabs` 배열. `TabId`의 `'admin'`, `'operations'`는 어떤 렌더 분기에도 연결되어 있지 않음.
2. **뮤테이션마다 전체 리로드**: `mutate()` → `refreshData()`가 `setLoading(true)`를 호출해 앱 전체가 `LoadingScreen`으로 교체됨(App.tsx 382행 `if (!authReady || loading)`). 저장 한 번에 모든 화면 상태(필터, 선택 항목, 스크롤)가 초기화됨.
3. **CRUD 공백**: 프로젝트 삭제·배정 인원 변경, 검토요청 수정·회수, 마스터 데이터(제품/업무/초대) 이름 수정, 담당제품 상태 수정이 UI에 없음(RLS는 대부분 허용하는데 화면이 없음).
4. **접근 회수 불가**: 초대(`allowed_users`) 삭제가 `profiles`/`auth.users`를 건드리지 않아, 퇴사·이동자가 계속 로그인 가능.
5. **장식용 UI**: 첨부 파일 드롭존(실제로는 URL 입력만 동작), "임시저장/초안 저장" 버튼(실제로는 그냥 닫기), 프로젝트 progress bar(실제 진척이 아니라 배정 인원 기반 임의 수치).
6. **오류 전달 부실**: Supabase/Postgres 원문 에러(영문)가 그대로 토스트로 노출, 성공/오류 토스트 구분 없음, 에러 바운더리 없음.
7. **운영 불일치**: 문서(`docs/DEPLOYMENT.md`, README)는 Cloudflare Pages를 안내하지만 실제 워크플로는 Cloudflare Workers(`wrangler deploy --assets`)로 배포. 워크플로 env 블록에 실제 운영 값이 하드코딩되어 있음(민감정보 노출 가능성 있음).
8. **테스트 공백**: App.tsx 내부 로직(우선순위 점수, 기한 계산, 화면 상태)은 전부 테스트 불가능한 위치에 있음.

### 1.7 개선 시 우선적으로 유지해야 할 기존 기능

- RLS 정책과 역할 불변식 트리거 전체 (마이그레이션 순서 포함)
- 초대 기반 프로필 자동 생성 흐름과 강제 비밀번호 변경 흐름
- 검토요청 상태 3단계(`pending / approved / rejected`)와 피드백 이력 — `pending`에서 피드백 가능, 최종 판단만 `approved`/`rejected`
- 우선처리 큐의 정렬 규칙(기한 임박 → 오래된 무기한 요청 → 프로젝트 마감 → 마스터 공백)
- 데모 미리보기 모드(환경변수 없이 동작)
- CSV 내보내기의 인젝션 방지 처리
- 삭제 2단계 확인 패턴
- 기존 테스트 4종(`format.test.ts`, `permissions.test.ts`, `migrations.test.ts`, `demoData.test.ts`)

## 2. 개선 방향 총괄

우선순위 기준: **P0** 즉시 수정(오류·빌드 실패·데이터/권한 손상 위험) / **P1** 핵심 사용성·핵심 기능 / **P2** 품질·유지보수성·운영성 / **P3** 있으면 좋음

| 구분 | 현재 문제 | 개선 방향 | 기대 효과 | 우선순위 |
|---|---|---|---|---|
| 시스템 목적 | 초대 삭제가 접근 회수로 이어지지 않음 (`allowed_users` 삭제 후에도 `profiles`·`auth.users` 잔존) | 사용자 비활성화 절차(운영 런북) + 초대 삭제 시 안내 문구, 중기적으로 `profiles.is_active` 도입 | 퇴사·이동자 데이터 접근 차단 | P0 |
| 시스템 목적 | 검토요청을 낸 뒤 수정·회수 불가, 프로젝트 배정 변경·삭제 불가 | 검토요청 회수/수정(요청자, `pending` 한정), 프로젝트 배정 편집·삭제 UI 추가 | 핵심 업무 루프의 완결성 확보 | P1 |

| UI/UX | 저장할 때마다 전체 화면이 로딩 화면으로 교체되고 화면 상태 초기화 | 초기 로딩과 백그라운드 갱신 분리(`loading` vs `refreshing`) | 깜빡임 제거, 필터·선택 유지 | P1 |

| 사용자 편의성 | 오류가 영문 Postgres 원문으로 노출, 성공/오류 토스트 동일 스타일 | 에러 코드→한국어 매핑 모듈, 토스트 tone 분리 | 실수 원인 즉시 이해 | P1 |

| 버그/안정성 | 런타임 에러 시 백지 화면(에러 바운더리 없음) | 최상위 ErrorBoundary + 새로고침 안내 | 장애 시 복구 경로 제공 | P2 |

| 운영 | 문서는 Pages, 실제 배포는 Workers로 불일치 | `docs/DEPLOYMENT.md`를 실제 파이프라인 기준으로 갱신 | 신규 운영자 온보딩 오류 방지 | P1 |

| 리팩토링 | App.tsx 4,336줄 + 데드코드 약 800줄 + styles.css 이중 토큰(`:root` 2개, 7행/2032행) | 데드코드 제거 → 화면별 파일 분할 → 데이터 레이어 추출 → CSS 토큰 단일화 | 변경 안전성·리뷰 가능성 확보 | P1~P2 |
| 리팩토링 | 날짜·우선순위 유틸이 App.tsx 내부에 있어 테스트 불가 | `lib/dates.ts`, `lib/priority.ts`로 추출 + 단위 테스트 | 핵심 정렬 로직 회귀 방지 | P2 |

## 3. 상세 개선 계획

> 각 항목은 독립적으로 착수 가능하도록 작성했다. 파일 분할(E-2)보다 앞선 항목은 현재 구조(App.tsx 단일 파일) 기준으로 기술한다.

### 개선 항목 A-1. 사용자 접근 회수(비활성화) 체계

- **분류**: 시스템 목적 / 운영
- **우선순위**: P0
- **현재 상태**: `MasterPanel`·초대 카드의 삭제 버튼은 `allowed_users` 행만 삭제한다(`deleteRow('allowed_users', …)`). `profiles`는 `auth.users`에 cascade로만 연결되어 있어, 이미 가입한 사용자는 초대 삭제 후에도 로그인과 데이터 접근이 가능하다.

- **현재 문제**: 모든 뮤테이션이 `if (supabase) { …insert… } else { setData(…) }` 이중 구현이다(예: `createReview` 1914~1961행, `assignProduct`가 `MasterPanel`과 죽은 `AdminPanel`에 중복). 새 기능마다 두 벌을 작성해야 하고 데모/실서버 동작이 어긋나기 쉽다.
- **리팩토링 목표**: 화면 코드는 `repo.createReview(input)` 하나만 호출하고, Supabase 구현과 데모(인메모리) 구현이 같은 인터페이스를 만족한다.
- **변경 대상 파일**: 신규 `src/data/repository.ts`(인터페이스), `src/data/supabaseRepository.ts`, `src/data/demoRepository.ts`, 각 화면 파일
- **변경 방식**: 엔터티 하나씩 점진 전환(권장 순서: reviewRequests → projects → masterData). 전환 기간 동안 기존 분기와 공존 허용. 데모 구현은 기존 `setData` 로직을 그대로 이식.
- **기존 기능 보존 방법**: 엔터티 단위 커밋, 각 단계에서 데모 모드로 해당 화면 CRUD 수동 확인. `refreshData`는 마지막에 `repo.fetchAll()`로 이관.
- **테스트 방법**: demoRepository는 순수 함수화가 가능하므로 vitest로 생성→조회→수정→삭제 시나리오 테스트 작성. supabaseRepository는 쿼리 빌더 호출 형태만 스냅샷(선택).

### 개선 항목 E-3. styles.css 토큰 단일화

- **분류**: 리팩토링
- **현재 문제**: `src/styles.css`(약 4,460줄)에 `:root` 블록이 2개(7행, 2032행) 존재한다. 뒤의 "paper" 팔레트가 앞 블록을 덮어써서 앞 블록 대부분이 죽은 선언이며, 데드코드 컴포넌트 전용 클래스(`.assignment-board`, `.mini-columns` 등)도 남아 있다.
- **리팩토링 목표**: 토큰 1세트, 사용 중인 클래스만 남긴 CSS.
- **변경 대상 파일**: `src/styles.css`
- **변경 방식**: (1) C-1 이후 미사용 클래스를 `git grep`으로 확인하며 삭제, (2) 첫 번째 `:root`에서 두 번째 블록이 덮어쓰지 않는 유효 변수(`--sidebar-w`, `--ease-*`, `--dur-*`)만 두 번째 블록으로 병합 후 첫 블록 제거, (3) 섹션 주석으로 화면별 구획 정리.
- **기존 기능 보존 방법**: 화면별 스크린샷 비교(데모 모드, leader/member × 주요 5화면, 모바일 뷰포트 640px 포함).
- **테스트 방법**: 시각 회귀 수동 비교. 이후 자동화가 필요하면 Playwright 스크린샷 테스트 도입(P3).

## 4. UI/UX 개선안 상세

### 화면 1. 로그인 / 가입 (`AuthPanel`)

- **현재 문제**: (1) 미초대 사용자가 로그인해도 화면 변화가 없음(B-3). (2) 로그인 비밀번호 `minLength=4`(임시 비밀번호 수용)와 가입 `minLength=8`이 다른 이유가 화면에 설명되지 않음. (3) 가입 성공 시 이메일 확인 필요 여부가 Supabase 설정에 따라 달라지는데 안내가 없음(**확인 필요**: 프로젝트의 이메일 confirm 설정).
- **개선 방향**: 상태별 명확한 다음 행동 안내.
- **추가 또는 변경할 UI 요소**: 미초대 상태 안내 화면(B-3), 로그인 폼 하단에 "처음 받은 임시 비밀번호로 로그인하면 비밀번호 변경 화면으로 이동합니다" 캡션, 가입 완료 시 이메일 확인 필요 여부 안내 문구.
- **사용자의 기대 흐름**: 초대받음 → 임시 비밀번호 로그인 → 비밀번호 변경 → 홈. 초대 안 받음 → 명확한 안내 + 파트장 문의.
- **예외 상황 처리**: 비밀번호 오류(영문 Supabase 메시지)를 한국어로 매핑(B-2), 네트워크 실패 문구 제공.
- **완료 기준**: 신규 인원이 문서 없이 첫 로그인을 완료할 수 있다.

### 화면 2. 파트장 홈 (`LeaderDashboard`)

- **현재 문제**: (1) 우선처리 큐 항목을 클릭하면 대상 탭으로 이동만 하고 해당 항목이 선택되지 않아, 목록에서 다시 찾아야 함. (2) "팀 워크로드"의 부하 판정 기준(합계 8/5)이 화면에 설명되지 않음. (3) 최근 활동이 6건 고정이고 더 보기가 없음.
- **개선 방향**: 큐 → 상세로 직행하는 딥링크형 이동.
- **추가 또는 변경할 UI 요소**: `setActiveTab`을 `navigate({ tab, entityId })` 형태로 확장해 `ReviewsPanel`이 `initialSelectedId`를 받도록 변경(B-1과 함께 하면 상태 유지가 쉬움). 워크로드 배지에 `title` 툴팁("제품+업무+프로젝트+미완료 검토 합계 기준"), 최근 활동에 "전체 보기" 버튼(활동 로그 화면 또는 40건 확장).
- **사용자의 기대 흐름**: 출근 → 홈 → 큐 최상단 클릭 → 바로 해당 검토요청 상세에서 피드백 작성.
- **예외 상황 처리**: 큐 대상 항목이 삭제·회수된 경우 목록 첫 항목 선택 + "요청이 회수되었습니다" 안내.
- **완료 기준**: 큐 클릭에서 피드백 작성까지 추가 탐색 0회.

### 화면 3. 검토요청 (`ReviewsPanel` — 파트장/파트원 공용)

- **현재 문제**: (1) 저장마다 선택·필터 초기화(B-1). (2) 종결 요청이 진행 요청과 섞이는 정렬(C-5). (3) 파트원이 요청 회수·수정 불가(A-2). (4) 첨부 드롭존이 장식(B-4). (5) 반려 시 사유 입력이 강제되지 않아 파트원이 이유를 모를 수 있음.
- **개선 방향**: 목록은 "진행 중 우선", 상세는 "행동 완결".
- **추가 또는 변경할 UI 요소**: 상태 전환 버튼에서 `rejected` 선택 시 사유 입력을 요구하는 소형 confirm(피드백 입력란에 포커스 + "반려 사유를 남겨주세요" 안내로 대체 가능), 요청자용 "수정/회수" 버튼(A-2), 목록 정렬 개선(C-5), 상태 필터를 select 대신 탭형 세그먼트(기존 `status-summary` 배지를 클릭 가능하게 전환해 중복 UI 제거).
- **사용자의 기대 흐름**: 파트원: 작성 → 대기 → 피드백 알림 확인 → 종결 확인. 파트장: 필터(대기) → 상세 → 피드백 → 상태 전환 → 다음 항목.
- **예외 상황 처리**: 빈 목록 상태 문구는 필터 조건을 포함("'반려' 상태의 요청이 없습니다"), 첨부 링크가 http/https가 아니면 저장 전 인라인 오류 표시(현재는 throw 후 토스트).
- **완료 기준**: 반려된 모든 요청에 사유 피드백이 1건 이상 존재하고, 진행 중 요청이 항상 종결 요청보다 위에 온다.

### 화면 4. 프로젝트 (`ProjectsPanel`)

- **현재 문제**: (1) 배정 변경·삭제 불가(A-3). (2) 상단 "상태 보드"와 하단 "배정 현황" 섹션에 검색창·상태 필터·CSV 버튼이 중복 배치되어 같은 상태를 공유하는지 혼란. (3) 가짜 progress bar(B-4). (4) 마감일에 과거 날짜 입력 가능(경고 없음).
- **개선 방향**: 조회(보드)와 관리(목록)의 역할을 나누고 컨트롤은 한 곳으로.
- **추가 또는 변경할 UI 요소**: 툴바를 페이지 상단 1개로 통합(두 섹션이 동일 `projectQuery`/`statusFilter` state를 이미 공유하므로 UI만 정리), 프로젝트 카드에 "배정 편집"·"삭제" 진입점(A-3), 마감일 입력 시 과거 날짜면 "이미 지난 날짜입니다" 인라인 경고(저장은 허용 — 소급 등록 케이스 존재), progress bar → "배정 n명 · D-x" 메타 라인으로 교체.
- **사용자의 기대 흐름**: 파트장: 생성(배정 포함) → 진행 중 상태 전환 → 인원 조정 → 완료 처리. 파트원: 내 프로젝트와 마감 확인.
- **예외 상황 처리**: 마지막 배정 인원을 제외하면 "담당자 없음" 카드 상태가 되는데, 이때 보드에 "담당자 미지정" 배지 강조.
- **완료 기준**: 프로젝트 라이프사이클(생성→조정→완료/삭제)이 화면 안에서 완결된다.

### 화면 5. 파트원 관리 (`TeamPanel`)

- **현재 문제**: (1) 관리 메모가 파트원 본인에게도 보인다는 사실이 화면에 표시되지 않음(RLS `profile_notes_select_self_or_leader`상 member 본인 열람 가능, member 홈에 "파트장 메모" 섹션 존재). placeholder("리스크 메모")가 비공개 메모로 오해하게 만듦. (2) 메모 삭제·수정 불가.
- **개선 방향**: 공개 범위를 명시하고 메모 관리 기능을 보강.
- **추가 또는 변경할 UI 요소**: 메모 입력란 위에 "이 메모는 해당 파트원에게도 표시됩니다" 캡션, 메모별 삭제 버튼(RLS `profile_notes_write_leader`가 이미 delete 허용 — UI만 추가), placeholder를 "배정 조정, 인수인계 등 공유 메모"로 교체.
- **사용자의 기대 흐름**: 파트원 카드 선택 → 배정 요약 확인 → 공유 메모 작성 → 파트원이 홈에서 확인.
- **예외 상황 처리**: 파트원 0명일 때 초대 관리로 안내하는 빈 상태 버튼.
- **완료 기준**: 메모의 공개 범위 오해 소지가 없고, 잘못 쓴 메모를 지울 수 있다.

### 화면 6. 마스터 (`MasterPanel` — 제품/업무/초대)

- **현재 문제**: (1) 등록 후 이름·코드·역할 수정 불가(삭제 후 재등록만). (2) 중복 등록 시 영문 unique 에러(B-2). (3) "선택 파트원 배정 현황" 섹션(3641~3660행)이 select와 배지 2개만 있는 빈 껍데기 — 배정 목록·삭제가 없어 용도가 불명확. (4) 초대 이메일 형식 검증 없음.
- **개선 방향**: 마스터 데이터의 등록-수정-삭제 3종 완결 + 배정 현황 섹션의 실질화.
- **추가 또는 변경할 UI 요소**: 카드별 인라인 수정(연필 아이콘 → 이름/코드 편집, `ProjectsPanel`의 `projectEdits` 패턴 재사용), 초대 폼 `type="email"` + 중복 사전 안내, "선택 파트원 배정 현황"에 담당제품/담당업무 목록과 배정 삭제 버튼 복원(죽은 `AdminPanel`의 `mini-columns` 구현을 이식 후 원본 삭제 — C-1과 순서 조율).
- **사용자의 기대 흐름**: 연초 셋업: 제품 일괄 등록 → 파트원별 배정 → 이후 수시 조정.
- **예외 상황 처리**: 제품 삭제 시 "배정 n건이 함께 삭제됩니다"에 실제 건수 표시(현재는 일반 문구).
- **완료 기준**: 오타 수정을 위해 삭제-재등록하는 일이 없어진다.

### 화면 7. 파트원 홈 / 내 담당 (`Dashboard` member 분기, `work` 탭)

- **현재 문제**: 사이드바 "홈"과 "내 담당"이 동일한 컴포넌트·동일 내용을 렌더링(`activeTab === 'dashboard' || activeTab === 'work'` 분기, 429~435행). 탭 라벨만 다르고 화면이 같아 사용자가 차이를 찾으려 헤맨다.
- **개선 방향**: "홈"은 오늘의 리마인더 중심, "내 담당"은 담당제품·정기업무 전체 목록 중심으로 분리. 분리 비용이 크면 "내 담당" 탭 제거가 차선.
- **추가 또는 변경할 UI 요소**: `MyWorkPanel` 신설 — 담당제품 테이블(제품명/코드/상태), 담당업무 목록, 제품 상태별 필터. 홈에서는 담당제품/업무 섹션을 요약 카운트로 축소.
- **사용자의 기대 흐름**: 홈에서 오늘 할 일 확인 → 내 담당에서 전체 담당 범위 참조.
- **예외 상황 처리**: 담당 0건이면 "아직 배정된 담당이 없습니다. 파트장에게 문의하세요" 빈 상태.
- **완료 기준**: 두 탭의 내용이 시각적으로 구분되고, 이동 시 무엇이 달라지는지 즉시 인지된다.

### 화면 8. 공통 셸 (`Shell`)

- **현재 문제**: (1) 토스트가 탑바 우측 텍스트라 눈에 띄지 않고 성공/오류 구분 없음(B-2). (2) URL 라우팅이 없어 새로고침 시 항상 홈으로 리셋되고, 특정 화면을 링크로 공유할 수 없음. (3) 새로고침 버튼의 결과(언제 갱신됐는지)가 보이지 않음(D-2의 "마지막 동기화" 표시로 해결).
- **개선 방향**: 최소 라우팅과 신뢰 가능한 피드백.
- **추가 또는 변경할 UI 요소**: `activeTab`을 URL 해시(`#/reviews` 등)와 동기화하는 경량 훅 `useHashTab`(라이브러리 불필요, `hashchange` 리스너 + 초기값 파싱), tone 있는 토스트, 마지막 동기화 시각.
- **사용자의 기대 흐름**: 브라우저 새로고침·즐겨찾기 후에도 보던 화면 유지.
- **예외 상황 처리**: 유효하지 않은 해시는 대시보드로 폴백. member가 leader 전용 해시 진입 시 홈으로 폴백(기존 렌더 분기의 `leaderMode` 가드가 이미 빈 화면을 막지만 폴백 명시 필요).
- **완료 기준**: 새로고침 후 같은 탭이 유지되고, Workers 배포에서 해시 방식이므로 서버 설정 변경이 없다.

## 5. 기능 개선 로드맵

## 6. 개발 작업 단위 분해

> 각 작업은 독립 PR 크기로 설계했다. 선행 조건이 없는 작업은 병렬 진행 가능.

### 작업 1: 빌드·테스트 기준선 확정
- **목표**: 현재 미커밋 변경(`index.html`, `src/App.tsx`, `src/lib/format.ts`, `src/styles.css`)을 포함한 상태에서 `npm test`와 `npm run build`가 통과함을 확인하고 커밋으로 고정.
- **작업 범위**: 명령 실행, 실패 시 원인 수정(타입 오류 등 최소 수정만).
- **수정 대상**: 실패 원인 파일에 한정.
- **제외 범위**: 기능 변경 일체.
- **선행 조건**: 없음.
- **구현 지침**: `npm ci && npm test && npm run build`. 실패 로그를 그대로 기록.
- **테스트 지침**: 명령 통과 자체가 테스트.
- **완료 기준**: 그린 상태의 커밋 해시 확보.
- **주의할 리스크**: 이 문서의 라인 번호는 이 기준선 기준. 이후 작업은 모두 이 커밋에서 분기.

### 작업 2: 배포 워크플로 자격증명 이동 및 문서 정합 (D-1)
- **목표**: 저장소 텍스트에서 운영 식별 값 제거.
- **작업 범위**: `.github/workflows/deploy-worker.yml` env를 `vars`/`secrets` 참조로 교체, `docs/DEPLOYMENT.md`·README를 Workers 기준으로 갱신.
- **수정 대상**: 워크플로 1개, 문서 2개.
- **제외 범위**: 배포 방식 변경(Workers 유지), 앱 코드.
- **선행 조건**: GitHub 저장소 설정 권한(Variables/Secrets 등록).
- **구현 지침**: 기존 "토큰 없으면 배포 스킵" 가드 패턴을 URL/키 미설정에도 확장.
- **테스트 지침**: `workflow_dispatch` 수동 실행으로 빌드+배포 성공 확인.
- **완료 기준**: `git grep`으로 운영 URL/키/계정 ID가 저장소에 없음.
- **주의할 리스크**: secrets 등록 전에 머지하면 배포 중단 — 등록을 먼저 수행.

### 작업 3: 데드코드 제거 (C-1)
- **목표**: 렌더 불가능한 코드와 도달 불가 탭 제거.
- **작업 범위**: `AdminPanel`, `OperationsGuide`, `Dashboard` leader 분기(및 member 전용으로 리네임), `Shell` 구 `tabs`·`tabDescriptions`, `TabId`의 `admin`/`operations`, 관련 CSS.

### 작업 4: 로딩 상태 분리 (B-1)
- **목표**: 뮤테이션·수동 새로고침 시 전체 화면 교체 제거.
- **작업 범위**: `initialLoading`/`refreshing` 분리, 탑바 갱신 인디케이터, "마지막 동기화 시각" 표시.
- **수정 대상**: `src/App.tsx`(`App`, `refreshData`, `mutate`, `Shell`), `src/styles.css`(소폭).

### 작업 5: 오류 처리·토스트 체계 (B-2)
- **목표**: 한국어 오류 매핑과 성공/오류 구분 토스트.

### 작업 6: 미초대 사용자 안내 (B-3)
- **목표**: 세션은 있으나 프로필이 없는 사용자에게 안내 화면 제공.
- **작업 범위**: `sessionWithoutProfile` 상태 추가, `BlockedProfile` 개선(로그아웃 버튼, 안내 문구), 렌더 분기 수정.
- **수정 대상**: `src/App.tsx`.
- **제외 범위**: 가입 이메일 확인 플로우 변경.
- **선행 조건**: 작업 1. (작업 12의 인증 경로 정리와 충돌 주의 — 먼저 하는 쪽이 기준.)
- **구현 지침**: `loadSession`과 `onAuthStateChange` 양쪽에서 `user 존재 && profileRow null` → `setSessionWithoutProfile(true)`.
- **테스트 지침**: 미초대 계정 로그인 → 안내 화면 → `allowed_users` 등록 → 재로그인 → 정상 진입.
- **완료 기준**: 미초대 로그인 시 로그인 화면이 무반응으로 유지되는 경로가 없다.
- **주의할 리스크**: 프로필 조회의 일시적 네트워크 실패를 "미초대"로 오판하지 않도록, 오류와 null 결과를 구분.

### 작업 7: 검토요청 회수·수정 (A-2)
- **목표**: `pending` 요청의 요청자 본인 수정·회수.

### 작업 8: 마스터 데이터 인라인 수정 + 입력 검증 (화면 6)

## 7. 리스크 및 주의사항

**기존 기능이 깨질 가능성이 있는 부분**
- 작업 4(로딩 분리): 리마운트가 사라지면 각 패널의 stale 선택 상태가 드러날 수 있음. 특히 `ReviewsPanel`의 `selectedReviewId` 보정 `useEffect`와 `TeamPanel`의 `selectedMemberId` 보정이 데이터 갱신 이벤트에서 올바르게 동작하는지 집중 확인.
- 작업 3(데드코드 제거): `deleteWarnings`, `AdminDeleteTable`, `FormGrid` 등은 살아있는 코드가 공유 — 제거 범위를 타입 에러 기준으로 보수적으로.
- 작업 13(파일 분할): import 누락·순환 참조. "이동만" 원칙과 커밋 분리로 통제.

**데이터 구조 변경 시 주의할 점**
- RLS 정책 변경(A-1 2단계, A-2)은 반드시 신규 마이그레이션 파일로 추가하고, 기존 파일을 수정하지 말 것(적용 이력 어긋남). `migrations.test.ts`의 텍스트 회귀 테스트를 함께 갱신.
- `profiles.is_active` 도입 시 `is_leader()` 같은 `security definer` 함수 경유 정책과의 상호작용을 전 테이블에서 재검증.
- 제품/업무 삭제는 배정 cascade — 실수 방지를 위해 삭제 확인 문구에 실제 영향 건수 표시(작업 8) 전까지는 운영자 교육으로 보완.

**인증 및 권한 관련 위험**
- 초대 삭제 ≠ 접근 회수(A-1)가 현재 최대 권한 리스크. 런북 반영 전까지 인원 변동 시 Supabase 대시보드에서 수동 삭제 필요.
- member의 검토요청 update 정책 추가 시 `with check`에서 `status`·`requester_id` 고정이 빠지면 상태 조작 통로가 생김 — 리뷰 필수.
- `must_change_password` 흐름: 자가 가입 사용자도 기본 true라 방금 만든 비밀번호를 다시 바꾸게 됨 — 온보딩 정책(관리자 발급 vs 자가 가입)을 결정해 트리거 기본값 조정 검토(**확인 필요**: 실제 운영 온보딩 방식).

**배포 환경 관련 위험**
- secrets 이관(작업 2) 순서 실수 시 배포 중단. Variables 등록 → 워크플로 수정 → dispatch 검증 순서 준수.
- 문서(Pages)와 실제(Workers)의 불일치가 남아 있는 동안 신규 운영자의 이중 설정 위험.
- 해시 라우팅(화면 8)은 Workers 정적 서빙과 호환되지만, 이후 path 라우팅으로 바꾸면 `--assets` SPA fallback 설정이 필요.

**UI 변경으로 인한 사용자 혼란 가능성**
- 토스트 위치·색 변경(작업 5), progress bar 제거(작업 10), "내 담당" 분리(화면 7)는 릴리스 노트 한 장(사내 공지)으로 안내.
- "임시저장" 라벨을 실제 저장으로 바꾸면 과거에 눌렀던 사용자의 기대와 달라짐 — 첫 사용 시 "초안이 이 기기에 저장됩니다" 안내 1회 표시.

**테스트가 부족한 영역**
- 화면 로직 전체(현재 컴포넌트 테스트 0건). 최소한 `ReviewsPanel`의 필터·정렬·작성 흐름은 Phase 4에서 Testing Library로 보강.
- RLS는 수동 검증 의존 — 시나리오 수행 기록(날짜·계정)을 TEST_PLAN.md에 남기는 관행 필요.
- CSV 내보내기 결과의 Excel 호환(한글 BOM) — 실제 Excel에서 주기적 확인.

**확인이 더 필요한 영역**
- `npm test`·`npm run build`의 현재 통과 여부(이번 세션 미실행) — 작업 1에서 확정.
- Supabase Auth 이메일 확인(confirm) 설정과 가입 UX의 정합.
- supabase-js `onAuthStateChange` 콜백 내 호출의 실제 교착 재현 여부(C-4).
- 운영 온보딩 방식(임시 비밀번호 발급 주체와 방법), Storage 사용 허가 정책, 무료 티어 백업 정책.
- `index.html`의 Google Fonts 외부 로드 — 사내망 인터넷 제한 환경이라면 셀프호스팅 필요 여부.

## 8. 최종 권고

**가장 먼저 해야 할 5가지 작업**
1. 작업 1 — 빌드·테스트 기준선 확정(모든 후속 작업의 전제)
2. 작업 2 — 배포 워크플로 자격증명 이동 + 문서 정합(P0, 저장소 위생)
3. 작업 16의 사용자 제거 절차 문서화(P0, 접근 회수 공백 즉시 보완)
4. 작업 3 — 데드코드 제거(이후 모든 diff의 크기와 위험을 절반으로 줄임)
5. 작업 4 — 전체 리로드 제거(체감 품질을 가장 크게 바꾸는 단일 변경)

**먼저 진행하지 않는 것이 좋은 작업**
- 상태관리 라이브러리(Redux/Zustand)·react-query 도입: 10인 규모 데이터에서 과설계. 작업 4·14로 충분.
- 전면 UI 리디자인·CSS 프레임워크 교체: paper 테마는 이미 일관적. E-3 정리로 충분.
- 실시간 동기화(Supabase Realtime), 이메일 알림 인프라: 앱 내 뱃지(Phase 3)로 먼저 검증 후 결정.
- path 기반 라우터(react-router) 도입: 해시 동기화로 요구 충족, Workers 설정 변경 불필요.

**최소 비용으로 효과가 큰 개선**
- 에러 한국어화(작업 5) — 파일 1개 신설 수준으로 일상 스트레스 제거
- 미초대 안내 화면(작업 6) — 수십 줄로 온보딩 문의 제거
- 드롭존 preventDefault + 라벨 정직화(작업 10 일부) — 데이터 유실 방지
- 초대 삭제 경고 문구 수정(작업 16 일부) — 한 줄 수정으로 권한 오해 제거

**장기적으로 구조 개선이 필요한 부분**
- App.tsx → 화면/컴포넌트/데이터 레이어 3층 분리(작업 11→13→14 순서). 이 순서를 지키면 각 단계가 독립적으로 되돌릴 수 있다.
- styles.css 토큰 단일화(E-3)와 화면별 CSS 구획.
- 테스트 피라미드: lib 단위 테스트(작업 11) → demoRepository 테스트(작업 14) → 핵심 화면 컴포넌트 테스트.

**이 시스템을 실제 업무용으로 안정화하기 위한 핵심 조건**
1. **권한의 완결**: RLS는 이미 강하다 — 남은 구멍은 "접근 회수"뿐이며, 이것이 닫혀야 인사 변동이 있는 실조직에서 쓸 수 있다.
2. **행동의 완결**: 만들 수만 있고 고치거나 물릴 수 없는 흐름(검토요청·프로젝트 배정)을 CRUD로 완결해야 도구가 메신저를 대체한다.
3. **피드백의 정직함**: 화면이 보여주는 것(버튼, 진행률, 로딩)과 실제 동작이 일치해야 10명이 매일 신뢰하고 쓴다.
4. **복구 가능성**: 주간 백업과 복구 리허설 기록이 있어야 무료 티어 운영을 정당화할 수 있다.
5. **회귀 방지 습관**: 마이그레이션 텍스트 테스트·RLS 수동 시나리오·데모 모드 스모크라는 기존 자산을 모든 PR의 관문으로 유지한다.
